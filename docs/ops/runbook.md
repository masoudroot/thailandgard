# Runbook عملیاتی (Q4-03)

_۲۸ اکتبر ۲۰۲۶ (۶ آبان ۱۴۰۵). مخاطب: مسعود، و هر کسی که اول صبح هشدار را می‌بیند._

هدف: وقتی چیزی خراب شد، تصمیم از قبل گرفته شده باشد. این سند جای فکر کردن در
لحظهٔ حادثه را می‌گیرد.

## ۱) نقشهٔ واقعی سیستم

| لایه | چیست | کجا تنظیم می‌شود |
|---|---|---|
| لبه و رندر | Vercel (`Server: Vercel`, منطقهٔ `fra1`) | پنل Vercel |
| دیتابیس و محتوا | Postgres روی Supabase | سکرت‌های مخزن + پنل Supabase |
| دیپلوی دوم | Prisma Compute، از `.github/workflows/prisma-deploy.yml` روی push به `main` و `dev` | Actions secrets |
| کارهای زمان‌بندی‌شده | `cycle-worker`, `factory-daily`, `gsc-daily`, `uptime-probe` | `.github/workflows/` |
| هشدار | تلگرام `gozaresh_tilandgard_bot` + Issue با برچسب `ops` | `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` |
| مهاجرت‌ها | `site/factory/migrations` و `supabase/migrations` | `npm run factory:migrate` |

**نکتهٔ مهم:** merge روی `main` هم Vercel را دیپلوی می‌کند هم `prisma-deploy` را.
یعنی یک merge می‌تواند دو محیط را همزمان عوض کند.

## ۲) آستانهٔ اعلام حادثه

حادثه = یکی از این‌ها. بقیه «کار عادی» است و صبر می‌کند.

| شدت | تعریف | پاسخ |
|---|---|---|
| **Sev1** | سایت برای کاربر ۵xx یا خالی است، یا لیدها ثبت نمی‌شوند | همان لحظه، هر ساعتی |
| **Sev2** | بخشی از سایت خراب است، یا SLO به `breached` رسید | در ساعات کاری، همان روز |
| **Sev3** | SLO `burning` (نیمی از بودجه رفته)، یا کار زمان‌بندی‌شده شکست خورد | روز کاری بعد |

منابعی که حادثه را اعلام می‌کنند:

- `uptime-probe` هر ۱۵ دقیقه؛ فقط وقتی **هر سه تلاش** شکست بخورد هشدار می‌دهد.
- `factory:slo-probe` وقتی نرخ خطا از ۰٫۵٪ بگذرد.
- Issue با برچسب `ops` در گیت‌هاب.

## ۳) تشخیص سریع

```bash
# ۱. آیا سایت بالاست؟ (۲۰۰ = سرویس و دیتابیس سالم)
curl -sS -o /dev/null -w '%{http_code}\n' https://thailandgard.ir/api/health

# ۲. اگر ۵۰۳ بود، بدنه می‌گوید کدام لایه
curl -sS https://thailandgard.ir/api/health

# ۳. چه هدرهایی برمی‌گردد (وجود CSP و بقیه)
curl -sS -o /dev/null -D - https://thailandgard.ir | head -20

# ۴. نرخ خطا و بودجهٔ خطا
cd site && npm run factory:slo-probe

# ۵. آیا دیپلوی آخر سالم بود؟ (Vercel → Deployments)
gh run list --limit 10
```

## ۴) سناریوها

### A. سایت ۵xx می‌دهد یا پایین است

1. `curl -I https://thailandgard.ir` — اگر ۵xx: مشکل سرویس است، برو مرحلهٔ ۲. اگر تایم‌اوت: مشکل شبکه یا DNS.
2. Vercel → Deployments. آخرین دیپلوی تولید را ببین. اگر همان لحظهٔ شروع خرابی بود، برو سناریوی B.
3. اگر دیپلوی سالم بود: Supabase → Database → سلامت پروژه را ببین. اگر دیتابیس خوابیده، برو سناریوی C.
4. اگر هر دو سالم بودند: `npm run factory:slo-probe` را بزن تا ببینی کدام مسیر می‌شکند، نه فقط اکستنشن.

### B. دیپلوی بد (رگرسیون بعد از merge)

**ترتیب درست: اول برگردان، بعد فکر کن.** هر دقیقه‌ای که صرف ریشه‌یابی می‌شود،
کاربر از دست می‌رود.

1. Vercel → Deployments → دیپلوی سالم قبلی → **Instant Rollback**.
2. تأیید: `curl -sS -o /dev/null -w '%{http_code}\n' https://thailandgard.ir` و یک بازدید واقعی صفحهٔ تور.
3. اگر `prisma-deploy` هم همان merge را گرفته، دیپلوی Prisma Compute را هم برگردان.
4. بعد از پایدار شدن: `git revert <commit>` روی یک شاخه، PR، چک سبز، merge. **revert از طریق PR، نه push مستقیم.**
5. علت را در Issue همان حادثه بنویس.

### C. دیتابیس در دسترس نیست

1. تأیید: یک مسیر وابسته به داده را بزن، مثلاً `curl -sS -o /dev/null -w '%{http_code}\n' https://thailandgard.ir/tours`.
2. Supabase → وضعیت پروژه. اگر پروژه pause شده، از پنل resume کن.
3. اگر پروژه فعال است ولی اتصال نمی‌شود: سقف اتصال‌ها را ببین. `lib/factory/db` یک pool مشترک دارد.
4. فرم‌ها در این حالت ۵۰۰ می‌دهند با پیام «ثبت ناموفق بود؛ لطفاً مستقیم تماس بگیرید» — یعنی کاربر به تلفن هدایت می‌شود. این عمدی است؛ تغییرش نده.
5. لیدهای از دست رفته قابل بازیابی نیستند. بعد از حادثه، بازهٔ خرابی را با Clarity و لاگ تلگرام تطبیق بده.

### D. کار زمان‌بندی‌شده شکست می‌خورد

1. `gh run list --workflow=<name>.yml --limit 5`
2. `gh run view <id> --log-failed`
3. اگر سکرت است: Settings → Secrets. نام سکرت را عوض نکن، فقط مقدارش را به‌روز کن.
4. اگر کد است: همان مسیر شاخه → PR → merge.

### E. نشت سکرت (بدترین حالت)

1. **اول باطل کن، بعد پاک کن.** سکرت را در منبعش (Supabase / Vercel / BotFather) revoke کن.
2. مقدار جدید را در Actions secrets و Vercel env بگذار.
3. دیپلوی مجدد تا مقدار جدید بنشیند.
4. اگر توکن تلگرام بود: BotFather → Revoke، سپس `TELEGRAM_BOT_TOKEN` را به‌روز کن.
5. تاریخچهٔ گیت را بازنویسی نکن؛ سکرت باطل‌شده بی‌ارزش است و بازنویسی تاریخچه ریسک بزرگ‌تری دارد.

## ۵) فریز

فریز یعنی: **هیچ merge ای به `main` نمی‌رود مگر اصلاح همان حادثه.**

- فریز خودکار: وقتی SLO `burned` است یا حادثهٔ Sev1 باز است.
- فریز دستی: قبل از کمپین، آخر هفته‌های پرترافیک، یا وقتی مالک در دسترس نیست.
- پایان فریز: وقتی چک `test` سبز است، SLO به `ok` برگشته، و Issue حادثه بسته شده.
- در فریز، کارهای غیرفوری در شاخه‌ها جمع می‌شوند و بعد از پایان فریز یکی‌یکی می‌آیند.

## ۶) تماس با مالک

| چه زمانی | چطور |
|---|---|
| Sev1 هر ساعتی | تلگرام مستقیم مسعود (`TELEGRAM_CHAT_ID` = چت مسعود) |
| Sev2 در ساعات کاری | همان روز، پیام تلگرام |
| Sev3 | روز کاری بعد، در Issue |

اگر ۳۰ دقیقه پاسخ نیامد و حادثه Sev1 است: rollback را خودت انجام بده. برگرداندن
یک دیپلوی بد، تصمیمی نیست که منتظر اجازه بماند.

## ۷) بعد از حادثه

یک فایل کوتاه در `docs/ops/incidents/<date>-<slug>.md`:

- چه شد (فقط واقعیت، با زمان)
- چطور فهمیدیم (کدام هشدار، یا کدام کاربر)
- چطور برگشت
- چه چیزی را عوض می‌کنیم که تکرار نشود — با یک تسک مشخص، نه یک جملهٔ کلی

بدون مقصر. هدف این است که دفعهٔ بعد سریع‌تر بفهمیم، نه اینکه کسی محکوم شود.

## ۸) شکاف‌های شناخته‌شده — عمداً نوشته شده

این‌ها را باید بدانی، چون در لحظهٔ حادثه غافلگیرت می‌کنند:

1. **`/api/health` تا ۶ آبان هیچ چیز را چک نمی‌کرد.** فقط `{status:"ok"}` با کد
   ۲۰۰ برمی‌گرداند، حتی وقتی دیتابیس خوابیده بود؛ سبز بودنش یعنی «سرویس بالا
   آمده»، نه «سایت سالم است». از #266 به بعد یک خواندن واقعی از `site_settings`
   با بودجهٔ ۲ ثانیه انجام می‌دهد: `200 ok`، یا `503 degraded/down`، یا
   `200 ok/unconfigured` وقتی سکرت نیست. **قبل از #266 این هشدار وجود نداشت.**
2. **لاگ درخواست‌های Vercel از CI در دسترس نیست.** درصد واقعی ۵xx را نمی‌توانیم
   خودکار حساب کنیم؛ `factory:slo-probe` فقط **نمونه** می‌گیرد.
3. **محدودیت نرخ فرم‌ها درون‌حافظه‌ای است.** روی چند نمونه، هر نمونه شمارندهٔ خودش
   را دارد. برای فرم عمومی کافی است، ولی سقف واقعی چند برابر عدد اسمی است اگر
   ترافیک پخش شود.
4. **پایش از رانر گیت‌هاب اجرا می‌شود.** شبکهٔ داخلی ایران و مسدودسازی از سمت
   کاربر را نمی‌بیند.
5. **CSP در حالت Report-Only است.** گزارش‌ها را Vercel جمع می‌کند و فعلاً کسی
   آن‌ها را نمی‌خواند. یعنی CSP امروز محافظت نمی‌کند، فقط مشاهده.
6. **محتوا fallback دارد.** `lib/db-content.ts` وقتی خواندن دیتابیس شکست بخورد،
   به دادهٔ پیش‌فرض درون‌کد برمی‌گردد. پس صفحه «سالم» دیده می‌شود در حالی که محتوا
   کهنه است؛ این عمدی است، ولی یعنی «صفحه بالا می‌آید» سند تازگی محتوا نیست.
