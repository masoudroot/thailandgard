## 2. Codebase audit (Compute compatibility)

Checked across `site/app`, `site/lib`, `site/components`, `site/scripts`:

- **Edge runtime:** none. No `export const runtime = 'edge'` anywhere. Compute supports Node only, so nothing to convert.
- **ISR / revalidate:** none in code. (Only a comment in `app/sitemap.ts` explaining why `revalidate` was removed under Next 16 `cacheComponents`.)
- **`next/image`:** one usage, `site/components/blocks/hero.tsx` line 1 and 55, local file `/images/hero-phuket-sunset.webp`. No remote images. Works on Compute via the built-in optimizer (sharp now a direct dependency). Each optimization costs Compute requests/vCPU, but it is one image and cached after first hit.
- **`middleware.ts`:** none.
- **`vercel.json`:** none.
- **`@vercel/*` imports or Vercel APIs:** none in code. (Comments in `app/api/internal/content-sync/route.ts` mention Vercel; comments only, no code dependency.)
- **WebSockets:** only in `site/scripts/shoot.mjs` (a local screenshot/dev script, never deployed).
- **Filesystem writes:** `site/lib/callback-store.ts` falls back to a local JSONL file (`data/callbacks.jsonl`) ONLY when Supabase env vars are missing. On Compute the env vars will be set, so the Supabase path is used. Open item: if env vars were ever missing on Compute, fallback writes would land on an ephemeral filesystem and be lost on restart. Acceptable, but worth knowing.
- **API routes** (`app/api/callback/route.ts`, `app/api/internal/content-sync/route.ts`): Node runtime compatible, no changes needed.
- **Dynamic sitemap** (`app/sitemap.ts`): uses `connection()` to read the DB live per request. Works on Compute; costs a few queries per crawler hit.
- **Build-time DB reads** (`site/lib/db-content.ts`): reads Supabase with the anon key during `next build`; falls back silently to the TS files if env is missing or the DB is unreachable, so the build never fails for DB reasons.

Net result: no code conversions were needed. The only functional changes are the standalone flag and the sharp dependency.

## 4. Open blockers / decisions needed before go-live

1. **Prisma project does not exist yet.** Someone must create the project in the Prisma Console (region ap-southeast-1, immutable) and connect the GitHub repo `masoudroot/thailandgard` (Console → project → Git → Connect). The Console can open the workflow as a PR automatically; the drafted workflow file covers the manual path.
2. **Secrets must be set in two places** (see checklist below): GitHub Actions secrets for build-time vars, Prisma Console Environment for runtime vars. Values are write-only in the Console; keep a private copy.
3. **GitHub Actions minutes budget.** Every deploy runs `npm ci` + `next build` on GitHub's runners (free: 2000 min/month shared). Dozens of deploys/day will eat this fast. Decide the deploy cadence before switching traffic.
4. **Apex domain.** `thailandgard.ir` (apex) needs ALIAS/ANAME support at the DNS provider for the Prisma CNAME flow; otherwise serve on `www.thailandgard.ir` and redirect the apex. Check the DNS provider before cutover.
5. **Free-tier headroom.** Tightest meter is 4 vCPU-hours/month; if the service stays warm, 360 GB-hours memory can also be exceeded. Behavior on exceeding quota is undocumented (throttle vs hard block). Monitor the Usage page after cutover.
6. **No global CDN.** Single-region (Singapore) serving; fine for the audience, but no edge caching like Vercel.
7. **ISR-style cache is per-instance memory.** Next 16 `cacheComponents` defaults survive only while the instance is warm; scale-to-zero drops them and they rebuild on demand.
8. **Vercel stays up as fallback** until the Prisma production URL is verified end to end (domain + TLS + content + forms).

## 5. Secrets checklist

**GitHub → repo Settings → Secrets and variables → Actions (build time):**

| Secret | Source | Used for |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase dashboard (Project Settings → API) | Build-time content reads |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase dashboard (Project Settings → API) | Build-time content reads |
| `PRISMA_SERVICE_TOKEN` | Prisma Console → project → service token (ONLY if the repo is not connected in the Console; otherwise OIDC is used and no secret is needed) | Deploy authentication |

**Prisma Console → project → Environment → Add variable (runtime, set for both PRODUCTION and PREVIEW):**

| Variable | Source | Used for |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase dashboard | Runtime (client + server) |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase dashboard | Runtime reads |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase dashboard | Server-only: lead inserts, content-sync route |
| `INTERNAL_CONTENT_SECRET` | Generate fresh (e.g. `openssl rand -hex 32`); must NOT equal the Vercel one if that one was ever shared | Guards `/api/internal/content-sync` |

Notes:
- Changing a Console env value does NOT redeploy; redeploy (or promote) after changing values.
- Console values are write-only; they cannot be read back. Keep a private copy outside the repo.
- Never commit any of these values to git.
